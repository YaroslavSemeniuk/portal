Project Overview
What we're designing

ClassScout NYC is a discovery platform that helps busy New York City parents find, compare, and choose children's classes, camps, birthday parties, and local activities. A foundational design system and brand direction already exist — the goal is to elevate them into an experience that builds immediate trust with parents.

Platform surface
Web application — homepage, search results, listing detail, navigation, and supporting flows. Mobile-first responsive across all breakpoints.
Existing foundation
Brand identity, color tokens, and component library are documented. This work builds on — and may refine — what already exists, depending on the tier.
Implementation context
A software engineer handles development. All deliverables are Figma-based and include specifications, component states, and responsive annotations.
Fixed constraint across all tiers: Native mobile app (iOS/Android) is not in scope. Scout AI screens and developer implementation review are included in Tier 3 only.

Execution Roadmap
How each tier runs

Every tier follows a structured sequence. The stages below reflect how the work is sequenced for each path — from kickoff to final handoff.

01
Audit & Priority Agreement
We review the current design system and live site together, identifying the visual decisions that most undermine parent trust. A short written brief captures the top 10 priority fixes and the rationale for each — establishing a shared agreement before any design work begins.
This stage involves
  • Design system review—Current tokens, components, and live site assessed against parent-trust criteria.
  • Priority fix list—Top 10 visual issues ranked by impact; delivered as a shared document for sign-off.
02
Component Refresh
Token-level decisions — color, type scale, spacing, border radius — are updated based on the agreed priority list. Affected components are rebuilt to reflect the new decisions. This stage produces the core of the deliverable: a design system where every component reflects the refreshed visual language.
This stage involves
  • Token updates—Color palette, type scale, and spacing grid corrected across the system.
  • Component rebuild—Buttons, cards, chips, badges, and navigation updated to match new tokens.
03
Screen Application & Handoff
The refreshed system is applied to three priority screens, demonstrating the full visual impact and giving the engineer concrete implementation references. The final Figma file is structured for immediate developer use — annotated, organized, and exported.
This stage involves
  • 3 screens applied—Homepage and search results updated; one additional screen per team agreement.
  • Figma handoff—Annotated file with component library, specs, and export-ready assets.
01
UX Review & Discovery
The current product is reviewed through the lens of a busy NYC parent — mapping where confidence is built, where it breaks, and which structural decisions create unnecessary friction before a booking intent is formed. The output is a clear priority screen list agreed with the team.
This stage involves
  • Navigation audit—Information architecture reviewed against parent decision flow.
  • Friction inventory—Key friction points documented with structural improvement recommendations.
  • Screen priority list—Agreed list of 6 priority surfaces with design sequencing rationale.
02
Reference Research & Visual Concept
We identify 2–3 products that have already earned the trust of their target audience — parent-facing or similarly credibility-driven platforms. One visual concept is designed from the selected reference direction and presented for team alignment before screen production begins. This checkpoint prevents wasted design effort on a direction the team would reject later.
This stage involves
  • Reference collection—2–3 product examples showing the target visual register; presented with rationale.
  • Concept screens—Homepage and listing card designed in proposed direction — first alignment checkpoint.
  • Brand adjustment—Color, typography, and spacing tuned to support the selected visual direction.
03
Priority Screen Design
With direction aligned, the six priority screens are designed in full — mobile-first, with desktop variants for each. Each screen is treated as a complete parent briefing: structured, trust-forward, and implementation-ready from the first pass.
This stage involves
  • 6 priority screens—Homepage, search results, listing detail, onboarding, saved, mobile navigation.
  • Mobile + desktop—Both breakpoints designed for each screen using the established responsive grid.
04
Design System & Developer Handoff
The UI Kit is rebuilt to reflect the new visual direction — every component used across the six screens documented with states, specs, and token annotations. The Figma file is structured for the engineer to implement directly without requiring ongoing design interpretation.
This stage involves
  • Component library—All components with hover, active, disabled, and loading states documented.
  • Token documentation—Color, type, spacing, and radius tokens annotated for the codebase.
  • Handoff file—Developer-ready Figma with measurements, specs, and export-ready assets.
01
UX Audit & Journey Mapping
The full product is reviewed end-to-end — navigation logic, information architecture, trust signal placement, and parent journey flow. Three core parent scenarios are mapped from entry to booking intent, revealing where the current structure supports decisions and where it creates doubt. The output establishes the strategic foundation for every design decision that follows.
This stage involves
  • Full product audit—Navigation, IA, content hierarchy reviewed against parent confidence-building criteria.
  • Parent journey maps—Discovery, comparison, and booking-intent flows mapped with friction annotated.
  • Priority screen plan—Complete screen list with sequencing and design dependencies agreed with team.
02
Moodboard & Direction Selection
Two distinct visual directions are researched, moodboarded, and designed as concept screens. Both are presented to the team with a clear rationale for each approach — what it communicates, what it prioritizes, and who it resonates with. The team selects one direction. Everything from Stage 3 onward is built from that decision.
This stage involves
  • Moodboard (×2)—Visual reference sets for each direction — tone, palette, type, and layout logic.
  • Concept screens (×2)—Homepage concept designed for each direction; comparable and clearly differentiated.
  • Alignment session—Live call to select direction and define what carries forward into production.
03
Brand Refinement
The existing ClassScout identity is refined — not replaced — to align precisely with the chosen direction. Color system, type pairing, logo application, and visual language rules are codified into a brand reference document that travels with the design system. The result: every future design decision has a clear, documented answer.
This stage involves
  • Color system—Full semantic and visual token set defined: primary, trust, warning, neutral, surface.
  • Type pairing—Heading and body typefaces confirmed; scale clamp values across all breakpoints.
  • Brand reference doc—Logo rules, icon style, photography direction, and do/don't guide — one page.
04
Complete Screen Design
All priority screens are designed in the refined brand direction — mobile-first, with desktop variants for each. Every screen is treated as a complete experience: trust signals placed intentionally, loading and error states designed, Scout AI logic surfaced transparently. This stage covers the full parent journey without gaps.
This stage involves
  • 10+ priority screens—Homepage, search, filters, listing detail, Scout AI, onboarding, saved, account, states.
  • Mobile + desktop—Both breakpoints for every screen; map split view for tablet/desktop search.
  • System states—Loading skeletons, empty states, and error recovery designed for all surfaces.
05
Design System Built to Scale
A complete Figma component library is built from the ground up — structured so the engineer can design new screens without needing a designer present. Every component is token-driven, documented with usage notes, and exported in formats that map directly to the existing codebase structure.
This stage involves
  • Full component library—Every component, every state, every breakpoint — documented and annotated.
  • Token system—Color, spacing, radius, and type tokens named to match the implementation layer.
  • Usage notes—Do/don't per component written for a developer — not a designer — audience.
06
Prototype, Handoff & Implementation Review
An interactive Figma prototype covers the three core parent flows, enabling the team to experience and validate navigation logic before implementation begins. Two dedicated sessions with the software engineer ensure clean asset delivery and answer technical questions on the spot. One implementation review round is included before launch.
This stage involves
  • Interactive prototype—Three flows clickable: discovery → detail, Scout AI search, onboarding.
  • Engineer sessions (×2)—Live handoff calls — assets, specs, and implementation Q&A addressed directly.
  • Implementation review—One design consistency review of the built product before the September 1st launch.
Open Questions
To confirm before we start

These points aren't blockers — they're clarifications that sharpen the scope and prevent scope creep once the project is underway.

01
Do you have an existing Figma file for the design system?
The design system is currently documented as a static HTML site. Working in Figma directly — vs. rebuilding from the HTML — affects the starting timeline.
02
Is Scout AI in scope for this engagement?
The design system includes Scout AI component specs. Designing the guided discovery flow adds 2–3 screens — only relevant for Tier 3, but worth confirming.
03
Desktop layouts — required alongside mobile, or mobile only?
The brief says mobile-first. If desktop is required for every screen (not just homepage and search), this is factored into Tier 2 and Tier 3 scope as stated.
04
Who is the final approver — Roland, the partner, or both?
Knowing who signs off on design direction and milestone approvals helps us sequence revision rounds correctly and avoid delayed feedback loops.
05
Can YARSY reference this project in portfolio and case studies?
Standard for our engagements. If there's a pre-launch embargo, we're happy to agree on a publication date after ClassScout goes live.
06
Payment terms: 50% upfront, 50% on final delivery?
Our standard model. Given the tight August 20 deadline, agreeing on terms this week ensures we can start immediately and meet the launch date without gaps.
