Design Estimate

Merchant Cabinet

A self-service cabinet for business clients who accept payments through the service. The merchant registers, creates shops, obtains integration keys, and tracks operations and balances without contacting support — which is the commercial point of the product: every task the merchant completes alone is a support ticket that never gets opened.

Interface language is English. This is a web cabinet with desktop as the primary platform, and the scope requires it to work fully on mobile as well. Rather than drawing every screen twice, the mobile effort is concentrated where the task is genuinely mobile — checking balances, scanning operations, opening a password link from an email — while forms simply reflow into a single column.

Scope of work Tap a block for details

Every screen in the cabinet plus four email templates, each in desktop and mobile states. The exact screen list is settled at the stage 1.1 gate, which is what the flow audit exists to produce. The two heaviest blocks account for 31% of the estimate.

Screencast and flow audit 20 h$600

The opening block and the reference point for everything after it. The current cabinet is walked screen by screen and recorded, then annotated against the written scope. The value is not the recording itself but what it surfaces: the places where the live product and the specification disagree, and the transitions nobody documented. Resolving those before design starts is what makes the stage 1.1 gate meaningful.

  • Full walkthrough of the live cabinet — every screen in scope, in the order a merchant meets them
  • Annotated recording — transitions, states, and the outcome of each step captured as they behave today
  • Gap list — where the running product diverges from the scope document, and which behaviour is intentional
  • Basis for the approval gate — the artefact the client reviews to confirm what is replicated and what changes
UI Kit / Design System 16 h$480

The foundation every other screen is assembled from. The cabinet is predominantly tables, forms, and cards, so the components are defined once and the interface is composed from them rather than drawn screen by screen. The work extends the existing DPay design system: components the cabinet needs but the system does not yet carry are added and folded back in, so the system grows with the project instead of forking away from it.

  • Colour palette and type scale — inherited from DPay, extended where the cabinet requires it
  • New and missing components — inputs, buttons, tabs, tables, cards, tooltips, a date range picker with presets, a currency switcher, and a markdown element set; whatever the current system lacks is built to its conventions, each in desktop and mobile variants
  • Element states — default, hover, disabled, error, loading, empty. Routinely omitted at estimate stage and the most expensive category to retrofit
  • Iconography — base set in a single style and stroke weight
Sign-in and registration 8 h$240

The front door, and the point where acquisition either completes or drops off. The underlying logic is not trivial: a single registration submit creates both the user and the merchant at once, after which the user lands on the merchant details screen. Access to the cabinet stays blocked until the merchant is configured, so that forced step has to read as onboarding rather than as an error.

  • Sign in — email and password, with links to password recovery and registration
  • Registration — email, password, confirmation, terms checkbox, and a link to the offer document
  • Merchant creation — a required step immediately after registration; technically it edits an already-created merchant, and the interface conceals that
  • Password reset request — the confirmation message appears even for unknown addresses, as protection against address enumeration; wording carries the security requirement
  • New password — opened from the email link, with a separate state for an expired link and a path to request a new one
  • Expired session — sessions end without warning because they cannot be extended, so Sign in carries a short "your session expired, sign in again" state. A state of the existing screen, not a new one
  • Service unavailable — a clear page in place of a technical error during scheduled maintenance
Shops and integration 40 h$1,200

The heaviest block alongside Operations, and the one that determines time-to-first-payment. Merchants connect on their own here, which is also where most of the risk sits: a newly created shop cannot accept payments until keys are issued and currencies are enabled. If the interface fails to communicate that, the merchant contacts support instead of going live. Two irreversible actions additionally need explicit guardrails.

  • Shop list — search by name, identifier, and status, with pagination; both the shop card and shop creation start here
  • Shop creation — name, description, website. A connection checklist appears immediately after creation, because the shop is not yet able to take payments
  • Shop card — General tab — name, description, website
  • Currencies tab — enabling a currency opens a real account for the shop and cannot be undone, so a toggle would be a control that lies. Each currency is a row with an explicit Enable action and a confirmation naming the consequence; once enabled, the row becomes a status without a control
  • API settings tab — signature algorithm, keys, and the allowed IP addresses
  • Keys and signature — shop identifier, four keys with copy-to-clipboard, the selected signature algorithm, and concise instructions for signing requests
  • Key regeneration — affects both key pairs and is irreversible. The confirmation dialog asks for the current password before it proceeds, and states plainly that the previous keys stop working
  • IP whitelist editing — adding, validating and removing allowed addresses. Only the addresses listed here can reach the service, so deleting the wrong one silently breaks a live shop; removal is confirmed before it applies
Dashboard 20 h$600

Originally scoped as a four-part summary inside Operations. The backend now serves nine indicators, which turns the landing screen into a proper analytics view — a chart, two breakdown tables, a metric grid and a connection checklist, each with a mobile counterpart. It is carried as its own line because it no longer behaves like part of the operations journal. With the currency question settled, the layout is fixed rather than variable, which is what holds the figure steady.

  • Turnover metrics — seven and thirty days, split between incoming payments and payouts
  • Turnover chart — daily figures across the month, the one visual element on the screen
  • Breakdown by payment system — a compact table alongside the chart
  • Health indicators — share of successful operations for the period, average ticket, average processing time
  • Latest ten operations — the shortcut into the journal
  • Connection checklist — shops missing keys or enabled currencies; the screen's main job is to stop those becoming support tickets
  • Currency switcher — monetary figures carry no combined total, so the screen shows one currency at a time from a switcher with a default selection. It sits alongside the merchant switcher, and the two together set the context for everything below them
Operations 28 h$840

The reason a merchant opens the cabinet daily: where the money is and what happened to a given payment. The difficulty is data density — payments and payouts share one table of roughly a dozen columns, and all of it must remain readable on a phone. Filters are a discipline of their own: they either close the "find this one operation" scenario or the merchant escalates to support.

  • Operations log — payments and payouts in a single table: identifiers, shop, type, status, amount, currency, creation and processing dates
  • Log filters — by shop, status, type and operation number, plus a date range picker with day, week and month presets and free selection of a start and end date
  • The log on mobile — eight data columns do not compress, so on a phone the log becomes a list of cards rather than a squeezed table. In practice this is a second design of the same screen, and it is where most of the mobile effort in this estimate goes
  • Operation card — the full record of a single payment: type and status, amounts and currencies, client account, description, dates, data passed by the shop, and return and notification URLs
  • Account balances — per shop currency: available amount, balance, holds, blocks, overdraft and rolling reserve. No account number and no combined total, so the screen is a set of per-currency rows rather than a summary
Operations export 12 h$360

Export is a flow, not a button. The merchant orders a file, waits while it is prepared, and collects it on a separate page. No new screens appear beyond those two — the work is in the states inside them. There is no push notification: the exports page polls and updates its own status, so the page has to make progress visible on its own.

  • Export request — format and period, ordered from the operations log. Two formats, CSV and XLSX
  • Five statuses — queued, preparing, ready, failed with a reason, and expired, each legible at a glance in the list
  • Self-updating page — status advances without a manual refresh, and the transition has to read as progress rather than as the page reloading under the merchant
  • Exports page — a separate screen listing requested exports with their status and download action. Files are kept seven days, after which the row turns to expired
  • Validation and limits — period capped at three months and ten files per shop, both surfaced on the form before the request is sent
  • Empty and unavailable states — before the first export is ordered, and while the feature is still being rolled out
Merchant 20 h$600

The legal-entity layer that shops and accounts belong to. At this stage a user holds exactly one merchant, and neither creating another nor inviting a user to one is available. The design nevertheless accommodates multiple merchants from day one, so the navigation does not require rebuilding when that capability ships — the dropdown switcher is planned in now at a fraction of the later cost.

  • Merchant list — currently displays the active merchant only, with a structure ready for several
  • Merchant switcher — a dropdown that sets the context for the entire cabinet
  • Merchant card — details: name, legal name, contact phone, email, and address. The merchant name cannot be changed after creation, so it is drawn read-only — visibly different from a disabled field a merchant could expect to unlock
Profile 12 h$360

Personal data for the individual user, as distinct from the Merchant block, which describes the company. The defining detail: changes are confirmed with the current password, so the form carries an additional verification step that cannot be presented as a plain "Save" without breaking the user's expectation.

  • User profile — email, phone, first name, last name, middle name, display name
  • Password confirmation — a separate step ahead of saving
  • Sign out — located here, visually separated from the remaining actions
  • Change password — current, new, and confirmation; a notification email follows the change
Documentation section 8 h$240

The integration reference, placed inside the cabinet so whoever connects a shop never has to leave it. Two screens carry it: a contents list and a single article. The text is written by the client — the design work is the reading experience around it: how a merchant finds the right page, keeps their place, and follows a long technical article on a phone.

  • Contents navigation — the section list, kept visible alongside the article being read
  • Article view — content arrives as markdown, so the design supplies a hierarchy for its elements rather than bespoke page layouts: headings, body, lists, code blocks and inline code, tables, quotes and links, all inheriting the type scale and colours already defined in the UI Kit
  • Mobile navigation — contents collapse on narrow viewports so the article keeps the screen
  • Loading and partial states — the content is still being written, so a half-filled section has to read as work in progress rather than as a broken page
Email templates 10 h$300

Transactional email in English — the cabinet extending beyond its own walls, and often the only brand contact a merchant has between sessions. No marketing campaigns or unsubscribe flows are planned, so the templates stay simple, but they belong to the same visual system as the cabinet and must render correctly across email clients.

  • Password reset — on user request, carrying the password change link
  • Welcome — after registration; states what to do next: create a shop, obtain keys, enable payment acceptance
  • Password changed — the fact and the time of the change
  • Keys regenerated — which shop, when, and a warning that the previous keys no longer work
Reviews, QA, handoff 22 h$660

A cross-cutting block spanning all three stages rather than a closing phase. It absorbs the revision cycles after each approval gate, verifies that every screen is built from the same components, and prepares files so development proceeds without clarification rounds.

  • Internal design reviews — ahead of every client showing
  • Feedback revisions — cycles following the approvals at stages 1.1 and 2
  • Visual consistency QA — spacing, states, typography, and behaviour across all breakpoints
  • Design file preparation and handoff — structured layouts, state specifications, asset export

Decision on record

Resolved

Money across several currencies

The cabinet holds no exchange rates, so no monetary figure can be reduced to a single number. Left open, this was the one item capable of moving the dashboard estimate: turnover is measured over two periods and split between incoming payments and payouts, and multiplying those four figures by an unknown number of currencies turns every metric tile into a table of variable height.

Agreed approach: a currency switcher on the dashboard, with a default currency. Every monetary indicator then shows one currency at a time, and the screen keeps a fixed layout regardless of how many currencies a shop has enabled.

This is what makes the dashboard figure firm rather than provisional. Two details are settled during design rather than now: which currency opens by default, and how the switcher presents itself to a merchant with only one currency — a dropdown holding a single option is a control that does nothing.

Account balances are unaffected and stay one row per currency: listing every currency side by side is the purpose of that screen, not a workaround for a missing total.

Assumptions

The figures hold while these remain true. A change to any one of them changes the estimate, and each is stated here so it can be confirmed or corrected before work begins.

  • Scope is fixed at the stage 1.1 gate The figures are based on the scope document as written. The flow audit produces the definitive screen list — if it comes out materially larger than the document implies, the estimate is revisited at the gate rather than absorbed. Once the flow is approved the list is locked, and anything added after that is quoted separately.
  • The DPay design system is extended, not replaced The cabinet is built on the existing DPay design system. The UI Kit allocation covers adding the components the current system lacks — tables, filters, key management, and the states the cabinet needs — and folding them back into the system so it grows rather than forks.
  • Interface copy and legal text are supplied by the client The offer document, terms, and email copy are provided as finished text. Copywriting is not included in the 216 hours.
  • Documentation and export are designed from a described flow Neither feature is running yet, so those screens follow the flow as the client described it rather than a working product. If the flow turns out differently once it is built, reworking the affected screens is quoted separately.
  • Feedback arrives within two business days per gate The six-week duration assumes that response time. Slower turnaround extends the calendar without changing the hours.
  • Design only — no frontend implementation The estimate covers design and handoff. Building the cabinet in code is a separate scope.
  • Refunds and test mode carry no design work Confirmed by the client: refunds and operation cancellation are not planned for the product, and a full test mode is deferred. Neither is designed here. If either returns, it is quoted as a separate line.
